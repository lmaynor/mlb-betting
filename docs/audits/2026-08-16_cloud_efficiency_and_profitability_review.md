# Cloud Efficiency & Profitability Code Review

Full exhaustive pass over the MLB pillar backend: every file in `mlb_core/`, `mlb/runners/`,
`mlb/training/`, `mlb/analysis/`, `mlb/systems/`, `main.py`, `deploy/*.sh`, and `scripts/*.py`
was read in full, line by line, by 7 parallel reviewers, each briefed on this repo's documented
contracts and historical bug classes (CONTEXT.md sections 1, 5, 6, 15, 16) so they wouldn't
re-report fixed issues, only regressions and genuinely new findings. I then personally
re-verified the ~6 highest-stakes claims directly against source (marked **VERIFIED** below)
before writing this up. Frontend (`beezy-vip/`) and `tests/`/`nba/` were out of scope.

**Total: ~120 findings** (after de-duplicating overlapping discoveries across batches).
Not all are fixes to make today — several are genuinely low-stakes. Triage by severity tag.

# PART A — Fix first

### A1. 🔴 `[PROFITABILITY]` **VERIFIED** — Kelly stake formula is computed against the wrong probability, inflating every bet's apparent edge and stake by roughly half the market's vig
- **Where:** `mlb_core/odds/utils.py:167-201` (`kelly_stake`, `kelly_pct`)
- **Grep:** `grep -n "edge = p_model - p_fair\|b = odds / 100 if odds > 0" mlb_core/odds/utils.py`
- **Why it matters:** The docstring mandates `edge = p_model - p_fair` (de-vigged probability), then feeds that into `f* = edge*(b+1)/b` where `b` comes from the **vig-inclusive** `odds`. The correct Kelly formula requires the *same* price basis on both sides: `b` and the probability subtracted from `p_model` must both come from the actual price being bet (breakeven prob = `1/(b+1)` = vig-inclusive implied prob), not the de-vigged fair prob. Since de-vigging always pushes `p_fair` below the vig-inclusive implied prob of the side being bet, every runner that calls `edge = model_prob - fair; kelly_stake(edge, odds, ...)` (confirmed verbatim in `run_hr.py:555`, `run_game.py:433`, `run_batter_hits.py:453`, `run_f5.py:347,514`, `run_nrfi.py:484`, `run_k.py:472,586,750`) is sizing every single stake larger than true Kelly, and can flag `kelly_triggered=True` on a bet that is objectively **breakeven-or-worse against the actual price taken** (any bet where `p_fair < model_prob < market_prob`). This is a distinct, additive contributor to the documented winner's-curse pattern (CLV going negative as stated edge grows), on top of the already-diagnosed model overconfidence.
- **Fix:** Keep `edge_vs_fair = model_prob - fair_prob` for gating (`min_edge`, `EDGE_CAP` — "does my model disagree with the sharp consensus" is a legitimate filter). Compute a **separate** `edge_vs_market = model_prob - american_to_implied_prob(odds)` and feed *that* into `kelly_stake`/`kelly_pct`, since `b` in those functions is derived from the same `odds`. Update the docstring's stated contract to match. This changes every historical stake/edge number's meaning — coordinate before shipping, and consider re-running `/edge-analysis` after the fix to see whether it moves the winner's-curse pattern.

### A2. 🔴 `[BOTH]` **VERIFIED** — The deploy script and the snapshot fetcher's own defaults both point back at the exact configuration that caused the documented 24+ hour SGO outage
- **Where:** `deploy/deploy_service.sh:53`; `mlb/runners/snapshot_odds.py:59-76,108-113,129-130`
- **Grep:** `grep -n 'set-env-vars="ODDS_PRIMARY' deploy/deploy_service.sh` → `53:  --set-env-vars="ODDS_PRIMARY=${ODDS_PRIMARY:-sgo}" \`; `grep -n 'os.environ.get("ODDS_PRIMARY", "sgo")\|if include_sgo is None: include_sgo = True' mlb/runners/snapshot_odds.py`
- **Why it matters:** `gcloud run services update --set-env-vars` **replaces** the full plain env-var map on the service (confirmed against this repo's own practice — CONTEXT.md §8 records the live `ODDS_PRIMARY=parlay` cutover/rollback both done via the merge-safe `--update-env-vars`, never via this script). `deploy_service.sh` is documented as the *only* sanctioned deploy path. Any deploy run without first `export ODDS_PRIMARY=parlay` silently pushes the service back to `sgo` — the exact setting that, combined with the current 8x/day snapshot cadence, took odds down for 24+ hours on 2026-08-09/10 (`docs/solutions/integration-issues/odds-primary-cadence-mismatch.md`). Independently, `snapshot_odds.py` itself defaults to `"sgo"` if the env var is ever unset for any reason, and `_gather_parlay`'s `include_sgo` parameter defaults to `True` (the expensive direction) if not explicitly passed — so even a future 9th scheduler job or a manual curl test that omits the flag reintroduces the incident with no code-level defense at all.
- **Fix:** In `deploy_service.sh`, switch to `--update-env-vars="ODDS_PRIMARY=${ODDS_PRIMARY:?Set ODDS_PRIMARY before deploying}"` (fails loudly instead of silently defaulting) or simply use `--update-env-vars` so a missing export leaves the live value untouched. In `snapshot_odds.py`, flip both defaults to the safe direction: `os.environ.get("ODDS_PRIMARY", "parlay")` and `include_sgo = False` when unset. Also: the empty-ParlayAPI-response fallback (`snapshot_odds.py:172-203`) calls `_gather_sgo()` unconditionally on *any* window, including the 4 windows deliberately configured `include_sgo=false` — a sustained ParlayAPI outage would silently reproduce 8x/day SGO load through a different trigger than the one already fixed. Gate that fallback behind the same budget logic, or don't fall back to SGO on `include_sgo=false` windows at all.

- **Where:** `mlb/runners/run_batter_tb.py` (whole `_build_predictions`, lines 166-346); `mlb/runners/run_1i.py` (whole `_build_predictions`, lines 219-350); `mlb_core/registry.py:69-90` (`"1IOU"` entry, `force_gate="on"`) vs `mlb_core/registry.py:203-213` (`"1I"` entry, no `force_gate`)

- **Why it matters:** Confirmed directly: neither file imports or calls `mlb_core.risk.calibration.apply()`, `EDGE_CAP`, or `mlb_core.risk.gates.is_suppressed()` anywhere. `run_batter_hits.py` — BATTER_TB's near-identical structural twin (same NegBin-CDF approach) — correctly wires all three at lines 400-402/452/454, strongly suggesting this was a retrofit that missed BATTER_TB entirely. Separately, decide deliberately whether `"1I"` should inherit `1IOU`'s `force_gate="on"` given they share the identical underlying discrimination problem, rather than leaving it unset by omission.

### A4. 🔴 `[PROFITABILITY]` **VERIFIED** — `build_game_features.py` inverts home/away pitcher attribution for ~28 of GAME's 42 features
- **Where:** `mlb/runners/build_game_features.py:284-285` (`build_starter_features`), `424-435` + `462-469` (`build_bullpen_features`, duplicated)
- **Grep:** `grep -n 'agg\["side"\] = agg\["inning_topbot"\].map({"Top": "away", "Bot": "home"})' mlb/runners/build_game_features.py`
- **Why it matters:** Top-of-inning = away team **batting** = **home** team's pitcher on the mound (the team not batting is the one pitching). This repo has the correct convention independently verified twice already: `build_nrfi_features.py:195-198` (`pitcher_is_home = (inning_topbot=="Top")`, explicitly "Verified 16/16 starts in diagnostics") and `build_f5_features.py:305-312`. `build_game_features.py` gets it backwards in both the starter-feature and bullpen-feature builders — confirmed by reading the code directly: its own comment asserts *"Top = away pitcher, Bot = home pitcher,"* the literal opposite of NRFI's verified comment. This is the *batting*-team formula (correct for `build_team_offense_features`, which correctly maps `Top→away_team`) copy-pasted into a *pitching*-team context, where the answer must be reversed. `config_game.py`'s `GAME_FEATURES` confirms all 16 starter + 12 bullpen columns are live model inputs. GAME's own docstring calls bullpen features "the KEY differentiator from F5" — this bug corrupts exactly that signal, and is a strong candidate contributor to GAME's documented weak metrics (AUC OOS 0.5565, best_iteration=15).
- **Fix:** Swap both branches: `agg["side"] = agg["inning_topbot"].map({"Top": "home", "Bot": "away"})`; `bullpen_pa["team"] = np.where(bullpen_pa["inning_topbot"]=="Top", bullpen_pa["home_team"], bullpen_pa["away_team"])` (both occurrences). **Before applying**, check `run_game.py`'s live-scoring feature construction for the same logic — if it's independently correct, train/serve have been mismatched the whole time (fix + full retrain); if it shares the inversion, the model was self-consistently trained on swapped labels (fix + full retrain either way, but the diagnosis differs).

### A5. 🔴 `[SECURITY][BOTH]` Nearly every state-changing or cost-incurring route in `main.py` has no authentication, and the Cloud Run service is open to `allUsers`
- **Where:** `main.py` — `/run`(129), `/build-all-features`(186), `/snapshot-odds`(249), `/settle`(286), `/refresh-data`(307), `/backfill-data`(375), `/backfill-savant`(511), `/monitor`(549), `/monitor-ops`(565), `/backfill-statcast`(581), `/dashboard`(679), `/capture-closing`(1442), `/monitor-drift`(1462), `/diagnose-nrfi-drift`(1477), `/retrain-outs`(1496), `/retrain-weekly`(1516), `/admin/backfill-notes`(1607)
- **Grep:** `grep -n "_auth_required" main.py` → only 12 hits, all on `/reset-and-run`, `/reset-bets`, and `/api/public/*` — none of the 17 routes above
- **Why it matters:** CONTEXT.md §13 confirms: *"Cloud Run service is now open to unauthenticated invocations (allUsers has roles/run.invoker)... scheduler routes... are still protected by OIDC tokens from the schedulers — they just aren't blocked at the IAM level anymore."* Cloud Run IAM is service-wide, not per-path — once `allUsers` holds `run.invoker` there is no IAM boundary on any route, and nothing server-side actually verifies the Scheduler's OIDC token (confirmed: the only `Authorization: Bearer` handling in the file is *outbound*, main.py calling other APIs). Anyone with the service URL can: repeatedly fire `/retrain-weekly` or `/retrain-outs` to trigger real, billed Cloud Run Job executions on demand and for free; POST `/backfill-data`/`/build-all-features` to tie up the single-worker service for up to an hour (see A6); or GET `/dashboard` for `model_prob`/`edge` on every bet — figures CONTEXT.md §13 says are deliberately hidden pre-launch.
- **Fix:** Add `err = _auth_required(request); if err: return err` to every route listed above except genuinely public reads. Longer-term, verify the Scheduler's OIDC token server-side (`google.oauth2.id_token.verify_oauth2_token`) rather than relying on IAM alone.

### A6. 🔴 `[BOTH]` The single gunicorn worker also serves the public site's live API, and several admin routes run their heaviest work in that same process for up to an hour
- **Where:** `Dockerfile:36` (`--workers 1 --timeout 3600`); `main.py:186-246` (`/build-all-features`), `375-508` (`/backfill-data`, docstring: *"Runs synchronously... Gunicorn timeout 3600s is adequate for a full season backfill"*)
- **Grep:** `grep -n 'CMD \[' Dockerfile`; `grep -n "Gunicorn timeout 3600s is adequate" main.py`
- **Why it matters:** `--workers 1` is intentional (avoid concurrent-write races during feature builds), but it means one OS process handles one request at a time for *everything*, including every `/api/public/*` route Vercel's SSR depends on for beezy.fyi's live pages. `/build-all-features` runs all 7 feature builders synchronously in-process (a duplicate, separate code path from the dedicated `mlb-build-all-features` Cloud Run Job) and can occupy the sole worker for up to an hour. Combined with A5 (no auth), any single request — accidental or not — makes beezy.fyi's live picks page return nothing for the full duration.
- **Fix:** Convert `/build-all-features`, `/backfill-data`, `/backfill-savant`, `/backfill-statcast`, `/admin/backfill-notes` to fire-and-return async triggers of their Cloud Run Jobs — the exact pattern `/retrain-weekly`/`/retrain-outs` already use correctly (call the Jobs `:run` API, return in seconds) — instead of running the heavy logic in-process.

### A7. 🔴 `[OTHER]` Two deploy scripts fight over the same `/run` scheduler jobs at different cron times, and `RUNBOOKS.md` tells you to run the stale one on every normal deploy
- **Where:** `deploy/setup_active_market_schedulers.sh` (whole script, upserts `mlb-betting-morning/evening` at `0 13 * * *`/`0 21 * * *` UTC) vs `deploy/setup_betting_schedulers.sh` (same job names, `0 16 * * *`/`0 22 * * *` UTC, paired with the odds-snapshot cadence); `RUNBOOKS.md:44,264`
- **Grep:** `grep -n 'upsert_job' deploy/setup_active_market_schedulers.sh`; `grep -n "setup_active_market_schedulers" RUNBOOKS.md`
- **Why it matters:** `setup_betting_schedulers.sh` was written one month after `setup_active_market_schedulers.sh` *specifically because* "the live morning/evening bodies omitted BATTER_TB and 1I" and was declared the new single source of truth — but the older script was never deleted, and `RUNBOOKS.md` (dated one day before the newer script was even written) still lists the old one as literal step 4 of the routine "Claude Code session → deploy" flow. Both scripts upsert the identical job names, so whichever runs last silently wins. Following the checked-in runbook exactly as written reverts scoring to 13:00/21:00 UTC — desynced from the odds-snapshot cadence — and drops the scheduler `--attempt-deadline` from 180s to 1800s. Because bet dedup is strict first-wins on `(system, game_date, game_pk, bet_type)`, a mistimed early run doesn't just miss opportunities, it can permanently lock in a stale price.
- **Fix:** Delete `deploy/setup_active_market_schedulers.sh` (its predecessor `add_betting_schedulers.sh` was already deleted for the identical reason, confirmed via git log) and fix `RUNBOOKS.md:44,264` to point at `setup_betting_schedulers.sh`.

### A9. 🔴 `[PROFITABILITY]` PITCHER_ER's suppression gate is wired in code but structurally can never fire
- **Where:** `mlb/runners/run_k.py:700` (`_score_pitcher_er` calls `is_suppressed("PITCHER_ER")`); root cause: `mlb_core/registry.py` has no `"PITCHER_ER"` entry, `mlb/runners/monitor_performance.py` never references it

- **Where:** `mlb/runners/run_f5.py:292-319`; `mlb/runners/run_k.py:206-214` (contrast with the correct version in `mlb/runners/run_nrfi.py:269-276`)

### A11. 🔴 `[BOTH]` OUTS's trained-model prediction uses the exact XGBoost pattern CONTEXT.md documents as crashing on XGBoost>=2.0
- **Where:** `mlb/runners/run_k.py:546-550`
- **Grep:** `grep -n "iteration_range=(0, _ntree_outs) if _ntree_outs else None" mlb/runners/run_k.py`
- **Why it matters:** `iteration_range=(0, ntree) if ntree else None` passes literal `None` whenever `best_ntree_limit` is falsy — the documented anti-pattern, banned by this repo's own contract. Every other predict call site in the codebase (including this same file's K-lambda path) correctly branches. Currently dormant only because the live OUTS model's `best_iteration=708` happens to be truthy; any future retrain that lands a falsy `best_iteration`/malformed meta crashes this call with no surrounding try/except, aborting the **entire** `run_k.py` scoring pass (both K and OUTS) for that run. The identical pattern also appears in `mlb/training/backtest_innings_windows.py:129` (F5 leg) — separate file, same fix.
- **Fix:** `ntree = getattr(_outs_booster, "best_ntree_limit", 0); pred = _outs_booster.predict(_dm_outs, iteration_range=(0, ntree)) if ntree else _outs_booster.predict(_dm_outs)` — matching the safe pattern already used elsewhere in this same file.

### A12. 🟠 `[PROFITABILITY]` K's starter-identification groupby drops one team's starter every game — corrupts both K and OUTS's entire historical training set and live rolling stats
- **Where:** `mlb/runners/build_k_features.py:77`
- **Grep:** `grep -n 'idx = bf.groupby("game_pk")\["bf"\].idxmax()' mlb/runners/build_k_features.py`
- **Why it matters:** `bf` has one row per (game_pk, pitcher) for every pitcher who appeared — both teams, starters and relievers. Grouping by `game_pk` alone and taking the single max-batters-faced row keeps only one pitcher for the whole game, silently dropping the other team's starter (plus every reliever). This is a *recurrence* of a bug already found and fixed elsewhere in this exact repo for the identical shape of problem (`mlb_core/data/auxiliary_features.py:1032`, the documented manager_hooks fix: "must group by `(game_pk, dominant_half)`, not `game_pk` alone"). Effect: roughly half of pitcher-game rows silently absent from K's `model_features.csv`, survivorship bias in every rolling K/OUTS feature, and CONTEXT.md's own documented finding that OUTS's `model_prob` AUC (0.559) badly trails `market_prob` AUC (0.637) now has a strong, concrete candidate root cause worth checking before any other OUTS remediation.
- **Fix:** Derive each pitcher's team first (`np.where(inning_topbot=="Top", home_team, away_team)`), then `idx = bf.groupby(["game_pk", "team"])["bf"].idxmax()`.

### A13. 🟠 `[PROFITABILITY]` Live weather/`is_outdoor` chaos: three different conventions across three code paths, plus a silent merge collision that erases the feature under its own name
- **Where:** `mlb_core/data/weather.py:131-139` (nightly training path — dome AND retractable both nulled, `is_outdoor=int(roof=="open")`) vs `mlb_core/data/weather.py:340-358` (live scoring path — only true domes nulled, `is_outdoor=1 if roof in ("open","retractable") else 0`) vs `mlb/runners/build_hr_features.py:242` (HR's own `agg["is_outdoor"]`, a third convention: any roofed park including open-retractable counts as never-outdoor) vs `mlb/runners/build_hr_features.py:616,618` (the weather-join merge, which has no suffix handling, so a fourth collision silently produces `is_outdoor_x`/`is_outdoor_y` instead of a usable `is_outdoor` column at all)

## C3. Training pipeline discipline

The team's own hard-won leakage fixes (70/10/20 split with test never touching early stopping,
calibrators fit train-only, `feature_dists` for PSI, NegBin `nb_alpha` via method-of-moments) were
applied to the four originally-audited systems (HR/F5/K/NRFI). The newer systems (GAME, BATTER_TB,
BATTER_HITS, OUTS) inherited most of this correctly — but not all of it, and two of the *original
four* have their own regressions nobody had re-checked since:

- **C3.1 🔴 NRFI's (both v17 and v18) walk-forward CV delegates to a shared helper (`mlb_core/models/base.py::XGBModel.walk_forward_cv`) that feeds the held-out test fold directly into early stopping** — the textbook C03 leak pattern, reintroduced via a shared helper neither retrain script shows on its own face. `mlb_core/models/base.py:43-76`, consumed by `mlb/training/retrain_nrfi_v17.py:362-373` and `retrain_nrfi_v18.py:327-341`. `grep -n 'watchlist = \[(dtrain, "train"), (dtest, "eval")\]' mlb_core/models/base.py`. Fix: carve an internal validation slice from `X_train` for early stopping inside `.train()`; use `X_test`/`y_test` only for the post-hoc metric.
- **C3.2 🔴 HR's own inline walk-forward CV loop uses the test fold as the early-stopping eval set directly** (`evals=[(dtest,"test")]`, no val carve) — the same bug class as C3.1, but HR-specific inline code, and HR is one of the four *originally audited* systems, meaning this part of that audit's fix never actually landed here even though HR's separate 70/10/20 outer split is correctly leak-free. `mlb/training/retrain_hr_v6.py:219-237`. ## C4. Backtest / bake-off methodology — false-positive and false-negative verdict risk

A bug in this layer doesn't just waste compute — it can produce a false "promote this system" or
false "kill this system" signal that both humans and the automated 200-bet gate trust.

- **C4.1 🔴 `backtest_market.OFFSHORE` — the denylist deciding which "books" are eligible for line-shopping and for the CLV closing-price reference — never excludes `"kalshi"`.** Kalshi quotes are written into `odds_history` under the exact same markets/systems as 6 live/gated systems. `_closing_index()` keys the CLOSING price purely by `(game_pk, player_id, selection, line)` with **no book in the key** — it can pick Kalshi's tighter no-vig price as "the closing line" for a real sportsbook bet, systematically biasing CLV negative and risking false `NO_EDGE` verdicts. - **C4.2 🔴 `backtest_market.backtest()` line-shops across an entire day's snapshot history, not a single decision epoch** — `drop_duplicates(subset=keys, keep="first")` after sorting by edge keeps the single highest-edge row seen *anywhere in that day's entire history*, when a live runner scores/bets at exactly two fixed times. - **C4.3 🟠 `verdict()` only checks CLV significance on the *low*-edge bucket and never inspects the *high*-edge bucket at all** — the documented winner's-curse pattern (small edge = good CLV, big edge = bad CLV) can clear `PROMOTE_CANDIDATE` completely invisibly, since nothing in `verdict()` computes or thresholds high-edge CLV, and the persisted handoff report (`bakeoff_report.EVIDENCE_COLS`) has no per-bucket CLV column at all — only the live stdout table shows it, and that's never captured to a file. `mlb/analysis/backtest_market.py:299-379`; `mlb/analysis/bakeoff_report.py:35-36`. `grep -n 'lo = cand\[cand\[.edge.\]' mlb/analysis/backtest_market.py`. # PART D — Security / access control

(Beyond A5/A6 above.)

- **D1. 🟡 `main.py`'s `/reset-bets` `player` filter is bound as a SQL parameter (not injectable) but unescaped inside an `ILIKE '%...%'` pattern** — an authenticated operator who includes a literal `%` in the filter deletes every bet for the date, not one player's. `main.py:664-665`. `grep -n "ILIKE :player" main.py`. Fix: escape `%`/`_`/`\` before interpolating into the LIKE pattern.
- **D2. 🟡 Two public routes build GCS storage keys directly from unsanitized `date`/`day` query params** — low exploitability against the GCS backend specifically (flat object names, not a filesystem), but a real path-traversal read primitive if `mlb_core.storage`'s documented local-filesystem dev mode is ever used with these routes exposed. `main.py:1057` (`/api/public/edge-enrich`), `main.py:929` (`/api/public/alerts/today`). Fix: validate both against `^\d{4}-\d{2}-\d{2}$` before building the key.
- **D3. 🟡 `main.py`'s `/dashboard` `days` param is f-string-interpolated into a SQL `INTERVAL` clause**, safe today only because of an upstream `int()` cast with no other defense. `main.py:709`. Fix: use a bound-parameter interval expression instead of relying on the incidental protection of an unrelated type cast.
- **D4. 🟡 `scripts/process_headshots.py` disables TLS certificate verification** (`ssl.CERT_NONE`) for an ordinary HTTPS call to the MLB Stats API, with no comment explaining why. Low stakes (only touches `beezy-vip/public/headshots/`), but opens a MITM door for no evident reason. `scripts/process_headshots.py:124-127`. Fix: remove the custom SSL context; use default verification.
- **D5. 🟡 `scripts/setup_discord.py` unconditionally deletes every channel and role in the guild with no confirmation guard or "already configured?" check** — a second accidental run would wipe the live notification channels the entire pipeline posts to. `scripts/setup_discord.py:72-91`. Fix: add a `--confirm` flag or a pre-check before the destructive loop.
